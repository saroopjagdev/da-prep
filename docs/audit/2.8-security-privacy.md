# 2.8 Security and privacy: audit

Date: 2 October 2026.

## How it was tested
- **Row-level security, for real:** the actual migration files were applied to an in-process Postgres (PGlite) with a minimal Supabase `auth` shim (`auth.users`, `auth.uid()`, `anon`/`authenticated` roles, Supabase's default table grants). Then cross-user and privilege-escalation attempts were run as two signed-in users and as an anonymous visitor. Script: kept in the session scratchpad; it will become a permanent test in Phase 3.
- Code review of every API route, the auth helpers, rate limiter, Stripe code and headers.
- `npm audit`; a secret scan of the code and the **whole git history**; `.env.example` compared with every `process.env` use; check that no client component imports server-only code; response headers read from the production build.

## Row-level security: **22 / 22 checks passed**
User A can read their own data and profile, but **cannot** read, update, delete or insert user B's data; can't use a collection name outside the allow-list or store more than 1 MB; can't read B's profile or usage; **can't make themselves Pro** (update or insert); can't reset their own usage; can't call the `consume_*` functions; can't read `ai_usage`. Anonymous visitors can't read any table. The server-side functions allow exactly 2 free uses then refuse, don't limit Pro, and deleting a user removes all their rows.

Caveat: the shim mimics Supabase; it isn't Supabase itself. The launch checklist records a manual two-user check on the live project, which agrees.

## Privacy notes (feed into 2.9)
- Data stored in the browser by default; cloud sync only when signed in. Good data minimisation.
- AI providers receive answers, statements and voice recordings. The privacy notice must name OpenAI, the purpose, and international transfer.
- No analytics today, so nothing to consent to; any analytics added later must respect the Children's Code (off by default for under-18s).

## Score: **8 / 10**
Reasons: database rules proven, clean dependencies and secrets, strong headers, careful deletion. Held back by the fail-open `ENFORCE_LIMITS` behaviour, the free-limit bypass, the in-memory rate limit without Upstash, and inline scripts in the CSP.

## To reach 9+
1. Fail closed in production: if `NODE_ENV=production` and accounts are configured, enforce sign-in on AI routes unless explicitly disabled.
2. Close the free-limit bypass (interview session id) and add a daily cost budget (see 2.6).
3. Require Upstash in production (health check warns if missing).
4. Add the RLS test to the repo's test suite (PGlite as a dev dependency) so policies can't silently regress.
5. Redact obvious personal data (emails, phone numbers) before sending to OpenAI.
6. Supabase auth: CAPTCHA and rate limits on magic-link requests (dashboard setting).
